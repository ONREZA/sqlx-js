# Upgrade to 0.30.0

This guide applies to applications upgrading from `0.29.x`.

This release replaces the JavaScript `Date` SQL boundary with Temporal, makes
`timestamp without time zone` an explicit query policy, and replaces the
vanilla PostgreSQL JSON boundary with Extended JSON protocol v1. It also makes
generated registries explicit, consolidates column assertions and lifecycle
events, and makes embedded SQL a prepare-owned artifact. It changes every
generated `json`/`jsonb` input and result type.

## Bind clients and install the Temporal provider

The current supported runtimes do not expose a compatible global Temporal API
by default. Install the peer provider and use TypeScript 5.4–6.x:

```bash
npm install @js-temporal/polyfill
npm install --save-dev "typescript@>=5.4 <7"
```

Generated contracts are no longer ambient, and there is no process-global
managed client. Bind each client to its generated registry and pass the
provider at that application boundary:

```ts
import { Temporal } from "@js-temporal/polyfill";
import { createSqlClient } from "@onreza/sqlx-js";
import type { SqlxJsGeneratedRegistry } from "./sqlx-js-env.js";
import queryDescriptors from "./.sqlx-js/runtime-descriptors.json" with { type: "json" };

export const db = createSqlClient<SqlxJsGeneratedRegistry>(undefined, {
  queryDescriptors,
  temporalApi: Temporal,
});
```

sqlx-js does not attach a polyfill to `globalThis`. If a future runtime exposes
a compatible native `globalThis.Temporal`, `temporalApi` can be omitted.

Replace package-level `sql`, `unsafe`, `ready`, `ping`, `snapshot`, and `close`
calls with the corresponding `db` member. Remove
`configureDefaultTemporalApi(...)`; the provider belongs to each client.
Reusable-query helper types now also require the registry explicitly, for
example `QueryParams<typeof query, SqlxJsGeneratedRegistry>` and
`SqlExecutor<SqlxJsGeneratedRegistry>`.

The ambient `KnownQueries`, `KnownFileQueries`, `KnownFunctions`, and
`KnownProfiles` interfaces were removed. Profiled clients use the generated
profile helper:

```ts
import type { SqlxJsGeneratedProfileRegistry } from "./sqlx-js-env.js";

const api = createSqlClient<SqlxJsGeneratedProfileRegistry<"api">>(databaseUrl, {
  execution: "adaptive",
  profile: { name: "api", role: "app_api" },
});
```

## Replace Date SQL values

Generated contracts now use these exact types:

| PostgreSQL | Previous | Current |
| --- | --- | --- |
| `date` | `PgTemporal` or `Date` | `Temporal.PlainDate` |
| `time` | `string` | `Temporal.PlainTime` |
| `timestamp` | `PgTemporal` or `Date` | `Temporal.PlainDateTime` |
| `timestamptz` | `PgTemporal` or `Date` | `Temporal.Instant` |

Replace `new Date(...)` parameters with the matching Temporal constructor.
Do not convert a wall-clock `timestamp` to an instant by appending `Z`; decide
whether the database value is a civil time or whether the column should migrate
to `timestamptz`. Temporal infinity is no longer exposed and fails explicitly.

The codec preserves microseconds returned by PostgreSQL; declared typmods such
as `timestamp(3)` still apply their server-owned precision. Inputs with
sub-microsecond precision now fail instead of being rounded. PostgreSQL `time`
24:00 also fails because `Temporal.PlainTime` has no exact representation.
`timetz` and `interval` remain strings because there is no faithful direct
Temporal representation for their PostgreSQL semantics. Leap-second values
also fail because Temporal would silently normalize `:60` to `:59`.

## Review timestamp without time zone queries

The default policy rejects every direct parameter/result and every physical
column mapped to a parameter that contains `timestamp without time zone`,
including arrays, domains, ranges, multiranges, and composites. For an
intentional civil-time query, add a named, source-local exception:

```ts
export const storeOpening = defineQuery.execute(
  "schedule.storeOpening",
  "INSERT INTO store_schedule (opens_at) VALUES ($1::timestamp)",
  {
    temporal: {
      timestampWithoutTimeZone: {
        allow: true,
        reason: "Opening time is local civil time, not an instant",
      },
    },
  },
);
```

For a project that predominantly stores civil times, set
`temporal.timestampWithoutTimeZone: "allow"` in config and use the local
`"reject"` override where an instant is required. Every PostgreSQL session is
pinned to UTC independently of this query policy. A later SQL or function
attempt to change `TimeZone` away from UTC or `DateStyle` away from ISO fails
closed and discards the affected connection.

## Audit before enabling writers

Run the new read-only inventory against every database that contains existing
application JSON:

```bash
sqlx-js json audit
sqlx-js json audit --json > extended-json-audit.json
```

Resolve every stored `$sqlx` collision, duplicate key, numeric token outside
the frozen PostgreSQL `jsonb` limits, and document above the cumulative
canonical-number budget reported as a blocker. The inventory
follows JSON leaves through PostgreSQL arrays, domains, and composites; review
the reported `jsonLeaves` paths for every containing column. Review the listed
indexes, constraints, generated columns, views, and source queries before
choosing tagged `bigint` or Temporal values: PostgreSQL sees those values as
tagged objects, not native numbers or strings. The command does not rewrite
data. Application migrations and backfills remain application-owned.

## Replace JSON parameter and result contracts

Generated parameters now require the branded document returned by
`sql.json(...)`:

```ts
// 0.29.x
type Input = JsonParameter<EventPayload>;

// 0.30.0
type Input = SqlxJson<EventPayload>;
```

Generated results no longer expose an ordinary mutable object:

```ts
const row = await db.sql.one("SELECT payload FROM events WHERE id = $1", id);

// 0.29.x: EventPayload
// 0.30.0: SqlxJson<EventPayload>
const event = row.payload.value;
```

`JsonParameter<T>` remains a deprecated type alias for source migration, but
generated declarations use `SqlxJson<T>` directly. Do not construct compatible-
looking objects manually; the runtime accepts only branded protocol documents.
The same rule applies to JSON leaves nested in PostgreSQL arrays, domains, and
composites; low-level `typed(...)` parameters are not a raw-text escape hatch.

## Choose the nested representation intentionally

Extended JSON supports nested `bigint` and all reconstructable Temporal types:

```ts
const payload = db.sql.json({
  eventId: 9_007_199_254_740_993n,
  occurredAt: Temporal.Instant.from("2026-08-04T10:15:30.123456789Z"),
  amount: JsonNumber.from("12345678901234567890.125"),
});
```

Use `bigint` or Temporal when JavaScript type round-trip matters. Use
`JsonNumber` when PostgreSQL must observe an exact native JSONB numeric for
operators, arithmetic, containment, or indexes. Use an ordinary string when a
temporal value must remain a JSONB string. Prefer a typed PostgreSQL column when
the value materially participates in constraints, joins, filtering, or order.

JavaScript `Date`, explicit `undefined`, class instances, custom `toJSON`,
accessors, sparse/named arrays, symbol keys, non-finite numbers, and unsafe
integer `number` inputs fail. Existing untagged large numeric result tokens
within the frozen protocol limits now decode as `JsonNumber` instead of failing
or rounding. `SqlxJson.parse` rejects duplicate keys, unknown tags/versions,
malformed controls, and fixed protocol resource-limit violations.

## Handle result decode errors by query and column

Client-side result codec failures now throw `ResultDecodeError`. The error
exposes the stable query ID, optional `defineQuery` name, zero-based column
index, output column name, PostgreSQL type OID, and original cause. The driver
does not attach the raw result value; a codec-supplied cause remains unchanged.
Existing code matching the codec's message can continue through `error.cause`;
prefer `instanceof ResultDecodeError` for new diagnostics. Rejected PostgreSQL
temporal infinity values also expose an `isfinite(...)` normalization hint.
This is a post-dispatch failure; retry autocommit mutations only when the
application provides idempotency.

## Review operator result nullability

Ordinary PostgreSQL operator results are now conservatively nullable even when
their operands are non-null. PostgreSQL operators are overloadable functions
without a catalog-level `RETURNS NOT NULL` contract; the previous inference was
unsound for JSON extraction and user-defined operators. `IS DISTINCT FROM` and
`IS NOT DISTINCT FROM` remain provably non-null, as do `IS NULL` and Boolean
tests. Review generated changes such as arithmetic and comparisons, including
`jsonb ->>` results. Where an application owns an exact stronger contract, use
a source-local result alias assertion instead of relying on the operator name.

## Consolidate column assertions

Move every `jsonbTypes` entry into `columnTypes`. `columnTypes` now owns direct
column assertions, including JSON/JSONB, JSON-backed domains, and JSON/JSONB
arrays. JSON values still use the `SqlxJson<T>` runtime boundary. Non-JSON
PostgreSQL arrays remain database-typed and use `arrayElementNullability` only
for an externally enforced element invariant.

Live prepare resolves every `columnTypes` and `arrayElementNullability` key
against PostgreSQL, including unused entries. Remove stale keys or fix their
relation, column, or PostgreSQL shape before regenerating artifacts.
Unqualified keys that match multiple schemas now fail; replace them with
`schema.table.column`.

## Use focused prepare only for local iteration

`prepare --include <glob>` and `prepare --query <name-or-id>` can validate a
selected source subset while reusing compatible cache entries. Their manifest
is explicitly incomplete: doctor, query freshness, and `prepare --check` fail
until a full live `sqlx-js prepare` succeeds. Do not commit or release focused
artifacts.

Complex pgschema projects can configure `schema.materializer` for disposable
`dev`/`verify`. The adapter receives the shadow URL through `DATABASE_URL` and
`SQLX_JS_SHADOW_DATABASE_URL` and must materialize all includes, roles, hooks,
ownership, and privileges. It inherits the process environment, and dropping
the shadow database does not remove cluster-scoped roles or extensions; use an
ephemeral PostgreSQL cluster when validation creates them. Target `pgschema
plan/apply` remains unchanged.

The managed provider is now pgschema 1.12.2. It preserves every function-local
`SET` entry, including settings such as `TimeZone`, across plan and apply.

Generated TypeScript object shapes for named composites and `RETURNS TABLE` /
OUT function results now use canonical field-name order. PostgreSQL ordinal
metadata remains unchanged for positional runtime codecs and schema snapshots.

Known utility statements are classified as `parse-only` from their PostgreSQL
AST before planning, so expected `PREPARE ...` syntax errors no longer pollute
server logs. Stale `expectedValidation: "parse-only"` annotations on plannable
queries are still detected.

## Make embedded SQL a prepare artifact

Replace `sqlx-js queries --embed <path>` with configuration:

```ts
export default defineConfig({
  sqlFiles: { output: "src/sql-files.generated.ts" },
});
```

Live prepare publishes that module atomically with declarations, descriptors,
enum output, and cache. Offline prepare regenerates it, verify compares it,
doctor audits it, and watch ignores the generated output. The `queries` command
is now read-only.

## Update runtime diagnostics and lifecycle observation

`NoRowsError` and `TooManyRowsError` now carry optional `queryId` and
`queryName`. `onQuery.durationMs` remains end-to-end; integrated managed clients
also expose optional `preDispatchDurationMs`, `acquireDurationMs`,
`executionDurationMs`, and `connectionCreated` so pool pressure is not reported
as slow SQL execution.

Replace `onQueryStart`, `onQueryTimeout`, `onQueryError`, and
`onClientStateChange` with one discriminated observer:

```ts
onLifecycle(event) {
  switch (event.kind) {
    case "query-start":
    case "query-timeout":
    case "query-error":
    case "state-change":
      observe(event);
  }
}
```

`onQuery`, `onQueryHookError`, and `onLifecycleHookError` retain their existing
roles.

## Regenerate artifacts

The query cache is now format 11, the declaration generator is revision 29,
runtime descriptors use format 4, and generated artifacts bind Extended JSON
protocol version 1. Regenerate every project from its schema authority:

```bash
sqlx-js dev --strict-inference
sqlx-js verify --strict-inference
tsc --noEmit
```

For a query-only project, run live `sqlx-js prepare --strict-inference` followed
by `sqlx-js prepare --check --strict-inference` instead of `dev` and `verify`.
Commit `.sqlx-js/`, `sqlx-js-env.d.ts`, and any configured enum or embedded SQL
output together. Do not hand-edit `PgTemporal` references in generated
declarations. A live prepare derives the new Temporal types and timestamp policy
facts from PostgreSQL. Old and new CLIs/runtimes fail closed on mismatched
artifacts. Roll back application code and all generated artifacts together if
the package version is rolled back.

## Reader-first rollout and rollback

Deploy in this order:

1. Audit collisions and JSONB-sensitive dependencies.
2. Deploy v1-capable readers while writers still emit vanilla JSON values.
3. Regenerate and deploy the v1 generated contracts.
4. Enable writers that may persist `bigint` or Temporal tags.

Before the first tagged write, rollback may restore 0.29.x and its matching
generated artifacts. After any tagged write, an old reader is unsafe: convert
the stored tags back through an application-owned migration before rollback.
Do not ask the 0.29.x CLI to read or rewrite format-11 caches or format-4 runtime
descriptors.
