# Upgrade to 0.31.0

This guide applies to applications upgrading from `0.30.x`. Version 0.31.0
replaces the vanilla PostgreSQL JSON boundary with Extended JSON protocol v1
and changes every generated `json`/`jsonb` input and result type.

## Audit before enabling writers

Run the new read-only inventory against every database that contains existing
application JSON:

```bash
sqlx-js json audit
sqlx-js json audit --json > extended-json-audit.json
```

Resolve every stored `$sqlx` collision and duplicate key reported as a blocker.
Review the listed indexes, constraints, generated columns, views, and source
queries before choosing tagged `bigint` or Temporal values: PostgreSQL sees
those values as tagged objects, not native numbers or strings. The command does
not rewrite data. Application migrations and backfills remain application-
owned.

## Replace JSON parameter and result contracts

Generated parameters now require the branded document returned by
`sql.json(...)`:

```ts
// 0.30.x
type Input = JsonParameter<EventPayload>;

// 0.31.0
type Input = SqlxJson<EventPayload>;
```

Generated results no longer expose an ordinary mutable object:

```ts
const row = await db.sql.one("SELECT payload FROM events WHERE id = $1", id);

// 0.30.x: EventPayload
// 0.31.0: SqlxJson<EventPayload>
const event = row.payload.value;
```

`JsonParameter<T>` remains a deprecated type alias for source migration, but
generated declarations use `SqlxJson<T>` directly. Do not construct compatible-
looking objects manually; the runtime accepts only branded protocol documents.
The same rule applies to JSON leaves nested in PostgreSQL arrays, domains, and
composites; low-level `typed(...)` parameters are not a raw-text escape hatch.

## Choose the nested representation intentionally

Extended JSON supports nested `bigint` and all reconstructable Temporal types:

```ts
const payload = db.sql.json({
  eventId: 9_007_199_254_740_993n,
  occurredAt: Temporal.Instant.from("2026-08-04T10:15:30.123456789Z"),
  amount: JsonNumber.from("12345678901234567890.125"),
});
```

Use `bigint` or Temporal when JavaScript type round-trip matters. Use
`JsonNumber` when PostgreSQL must observe an exact native JSONB numeric for
operators, arithmetic, containment, or indexes. Use an ordinary string when a
temporal value must remain a JSONB string. Prefer a typed PostgreSQL column when
the value materially participates in constraints, joins, filtering, or order.

JavaScript `Date`, explicit `undefined`, class instances, custom `toJSON`,
accessors, sparse/named arrays, symbol keys, non-finite numbers, and unsafe
integer `number` inputs fail. Existing untagged large numeric result tokens now
decode as `JsonNumber` instead of failing or rounding. `SqlxJson.parse` rejects
duplicate keys, unknown tags/versions, malformed controls, and fixed protocol
resource-limit violations.

## Regenerate artifacts

The query cache is now format 9, the declaration generator is revision 26,
runtime descriptors use format 4, and all three artifacts bind Extended JSON
protocol version 1. Run a live prepare and commit the complete replacement:

```bash
sqlx-js prepare
sqlx-js prepare --check --strict-inference
tsc --noEmit
```

Commit `.sqlx-js/`, `sqlx-js-env.d.ts`, and any configured enum output together.
Old and new CLIs/runtimes fail closed on mismatched artifacts.

## Reader-first rollout and rollback

Deploy in this order:

1. Audit collisions and JSONB-sensitive dependencies.
2. Deploy v1-capable readers while writers still emit vanilla JSON values.
3. Regenerate and deploy the v1 generated contracts.
4. Enable writers that may persist `bigint` or Temporal tags.

Before the first tagged write, rollback may restore 0.30.x and its matching
generated artifacts. After any tagged write, an old reader is unsafe: convert
the stored tags back through an application-owned migration before rollback.
Do not ask the 0.30.x CLI to read or rewrite format-9 caches or format-4 runtime
descriptors.
