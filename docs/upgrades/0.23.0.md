# Upgrade to 0.23.0

This guide applies to applications upgrading from `0.22.x`.

## Regenerate artifacts

The cache format is now 5 and the generator revision is 20. Regenerate the
query cache, runtime descriptors, and declarations against the intended
PostgreSQL schema:

```bash
sqlx-js dev --strict-inference
sqlx-js verify --strict-inference
tsc --noEmit
```

The cache now records inference provenance and parameter targets for
`sqlx-js queries explain <query-id>`.

## Bind generated clients explicitly

Generated registries require an explicit execution contract. Prefer the
descriptor artifact:

```ts
import { createSqlClient } from "@onreza/sqlx-js";
import type { SqlxJsGeneratedRegistry } from "./sqlx-js-env.js";
import queryDescriptors from "./.sqlx-js/runtime-descriptors.json" with { type: "json" };

export const db = createSqlClient<SqlxJsGeneratedRegistry>(undefined, {
  queryDescriptors,
});
```

Use `execution: "adaptive"` only as a deliberate transition:

```ts
export const db = createSqlClient<SqlxJsGeneratedRegistry>(undefined, {
  execution: "adaptive",
});
```

New `sqlx-js init` projects receive a user-owned `db.ts` and an initial
descriptor artifact. There is still no runtime filesystem discovery. The
global `sql`, `unsafe`, `ready`, `ping`, `snapshot`, and `close` exports are
deprecated but remain available for gradual migration.

Run `sqlx-js doctor` to review parameterized call-site coverage. Direct
descriptor clients are checked against the artifact; missing query entries are
errors. Explicit adaptive clients and options that cannot be classified
statically are listed for review.

## Review execution intent

Prepare now rejects `.one()` and `.optional()` statements without a result
set. Plain `sql()` for a statement without `RETURNING` warns and fails under
`--strict-inference`; change it to `.execute()`. `.execute()` with returned
rows warns because it discards them.

These diagnostics add no runtime branch. sqlx-js still does not attempt to
prove that arbitrary SQL returns exactly one row.

## Adopt savepoints where partial rollback is intentional

Transaction executors now expose `tx.savepoint(callback)`. Ordinary
PostgreSQL errors can be recovered through `ROLLBACK TO SAVEPOINT`. Managed
timeouts, aborts, and connection loss remain terminal for the whole outer
transaction and are never converted into a successful savepoint recovery.
Await the savepoint and use the executor passed to its callback; parent and
completed scoped executors reject work outside their ownership window.

## Rollout and rollback

Deploy generated declarations, cache entries, runtime descriptors, and
application code from the same revision. A `0.22.x` binary cannot consume the
new artifact revisions. Rollback therefore requires restoring the previous
application and its complete `0.22.x` artifact set together.
